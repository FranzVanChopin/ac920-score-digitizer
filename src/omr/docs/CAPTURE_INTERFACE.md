# 采集端与识别端的图像接口（2026-10-28）

本文对象：Codex 的采集固件 `software/camera_capture`，以及识别软件（`run_page.py` / `run_serve.sh`）。

依据：
- 2026-10-28 的样片：`Image/000004*.bmp`（全分辨率），`Image/04_sensor_bin2_*.bmp`（IMX477 2×2 合并）；
- 模拟实验：`sim_capture.py`；
- 清晰度测量：`measure_sharpness.py`。

## 1. 结论：识别端要什么样的图像

| 项目 | 规定 | 原因 |
|---|---|---|
| 分辨率 | **全分辨率 4056×3040，不合并像素** | 镜头稍模糊时更稳（见第 3 节）；整页实拍中，合并模式在字号小的乐谱上全部失败（第 2.1 节），不要送识别 |
| 格式 | **8 位灰度，无损**（PNG，或 8 位灰度 BMP） | 识别端本来就用这种灰度（OpenCV BGR→GRAY，即 BT.601）；样片 `000004_Grey.bmp` 与之逐点一致，数据量只有彩色的 1/3 |
| 采集端处理 | **可以裁到纸张（推荐，见第 1.1 节）；不做二值化、不做 CLAHE、不缩放** | 识别端会自行缩放到宽 1920、做 CLAHE，网络内部再二值化，这套流程是验证过的。预先二值化会丢失信息（第 3 节）；预先做 CLAHE 会被做两遍 |
| 方向 | **乐谱正立**：谱线水平，页面顶端朝上 | 单页入口 `run_page.py` 不会自动旋转。10-29 起 album 模式（`board_trial/album`）由识别端转正：`--rotate ccw`，即原始图像右边为页面顶端，所以采集端保持传感器原方向即可，但相机安装方向必须固定 |
| 取景 | **整页入画**，纸张四边都在画面内，纸张约占画面的 85–95% | 拍不到的内容，裁切也补不回来；谱表被切断时，分组和小节数都会出错 |
| 尺度 | 照片中谱线间距 **17–30 像素**（整页 A4 全分辨率竖拍：常规字号约 23 像素，小字号约 18 像素） | 缩放到宽 1920 后约 11–20 像素，在网络和规则的工作范围内；整页实拍 18 像素的识别结果不比 PDF 渲染图差（第 2.1 节）。近拍图约 60 像素，超出范围，只识别出约 12 个音 |
| 清晰度 | 全分辨率下五个区域的边缘宽度（10–90%）**都 ≤ 5 像素**，理想 ≤ 4 像素 | 模拟显示，约 5 像素以内准确率基本不变，7 像素时降到约 74%（第 3 节） |
| 曝光 | 纸面灰度约 190–235，墨迹 ≤ 90，不截顶 | 现在的样片纸面 206、墨迹 69，合格 |
| 写文件 | 先写临时文件，写完再改名为最终文件名 | 避免识别端读到写了一半的文件。现有固件的 `PHOTO.TMP` 正是这样做的 |

### 1.1 采集端裁切到 A4（推荐）

测试集里，camera67 的 65 页和开发板测试页都是纸张撑满画面、没有背景的图像。识别端的自动裁切在这 66 页上全部保留了整张图，所以识别流程本来就是在"已裁到纸张"的图像上验证的。采集端把桌面裁掉不但可以，还能缩小文件，并避免浅色桌面或阴影干扰识别端的自动裁切。

裁切要满足以下条件：
- **只裁到纸张边缘或略向外：** 可以留纸张边缘外 1–2% 的余量，绝不能裁进印刷区域。纸张自带的白边要保留。
- **最好做透视校正：** 由纸张四个角点做单应变换，拉正为矩形，谱线会更平直；只做轴对齐的矩形裁切也可以。
- **保持原始尺度：** 不缩小，整页宽度约 2400–2900 像素。插值用双线性或双三次。
- **找不准纸张时宁可不裁：** 四角检测不可靠时，输出未裁切的整幅图像，并在文件名或日志里标明。不要用固定位置去硬裁，一旦裁进内容，损失比留着桌面大得多。
- **方向和格式不变：** 裁切后乐谱仍要正立，仍是 8 位灰度、无损格式。

如果用支架把 A4 纸放在固定位置，也可以用一个固定的裁切框，稍大于纸张即可，这样最简单可靠。

**交接方式：** 识别端使用常驻流水线：

```
run_page.py --serve --pipeline   （或 run_serve.sh）
```

每有一张新照片，就向它的标准输入写一行：

```
<照片绝对路径>\t<新的输出目录>
```

每页的结果是输出目录下的 `page.musicxml` 和 `report.json`；程序在标准输出上每页打印一行 JSON。连续拍多页时，下一页的网络推理会和上一页的后续计算重叠。

采集固件现在跑在 A53 裸机上，识别软件跑在 Ubuntu 上，两者怎样合到一起（同一系统下运行，还是经 SD 卡交接）由 Codex 决定。只要满足上面的文件约定，识别端不需要改动。

**10-29 更新：** a4_album1 的 `Grey/SS-PP.bmp` + `Meta/SS-PP.json` 格式由 album 模式直接读取，方法是 `board_trial/album/run_album.sh 采集目录 输出目录 [--watch 1]`。三种融合方式见 `board_trial/album/README.md`。

## 2. 样片检查结果（`measure_sharpness.py`）

| 照片 | 谱线间距 | 边缘宽度（中心 / 四角） | 说明 |
|---|---|---|---|
| `000004.bmp`（全分辨率） | 59 px | 9.5 / 3.9–8.8 px | 近拍，只拍到局部页面；只有一角较清楚，可能是景深浅（约 ±3 mm）加纸面不平 |
| `04_sensor_bin2_color.bmp`（合并） | 30 px | 4.7 / 4.5–6.2 px | 同一画面；换算到纸面上的模糊程度与全分辨率相同 |
| 开发板测试页（电子版） | 24 px | 2.1 / 1.5–2.4 px | 理想参照 |

**用识别流程直接跑这几张近拍图：**
- 全分辨率灰度：找到 3 行谱、12 个音；
- 合并模式灰度：11 个音；
- 二值图：只有 6 个音。

画面里大约有 60 个音。原因是尺度过大，谱表也被画面切断了。这不是对准焦以后的真实水平，需要按第 1 节的要求拍整页，再评估一次。

**画面中的问题：**
- **细线锯齿：** 全分辨率图里，谱线和符干呈"麻绳状"锯齿，这是去马赛克在高对比细线上产生的拉链纹；合并模式下较轻。缩放到识别尺度后会部分平均掉，影响多大，要等整页实拍才能确定。建议 Codex 核对 `v_demosaic` 的 Bayer 相位和算法设置。
- **底色偏蓝：** 白平衡的问题，对灰度识别几乎没有影响。

### 2.1 整页实拍：镜头与光圈对比（2026-10-29）

详细结果见 `lens_compare/README.md`。

|---|---|

## 3. 模拟实验：分辨率、清晰度与二值化（`sim_capture.py`）

方法：
1. 把开发板测试页（谱线间距 24 px，相当于整页入画时的全分辨率照片）调成相机的灰度范围（纸 210、墨 70）；
2. 加上不同程度的高斯镜头模糊 σ（单位是全分辨率像素），以及噪声；
3. 分别按全分辨率、2×2 合并（平均）、二值化（局部均值）送进 v16 识别流程，统计正确音符数（共 263 个）。

| σ（px） | 边缘宽度（全分辨率 / 合并） | 全分辨率灰度 | 合并灰度 | 全分辨率二值 | 合并二值 |
|---:|---|---:|---:|---:|---:|
| 0 | 2.1 / 2.0 | 262 | 263 | 261 | 251 |
| 1.5 | 3.3 / 2.3 | 256 | 260 | 255 | 228 |
| 2.5 | 5.1 / 2.9 | 261 | 258 | 256 | 232 |
| 3.5 | 7.1 / 4.4 | 195 | 168 | 24 | 18 |

- **灰度好于二值：** 每一档都是灰度更好；模糊加重时，二值输入会彻底失败。
- **全分辨率与合并：** 清晰时两者差不多（相差 ±4 个音，属于单页的正常波动）；变模糊后全分辨率更稳（195 对 168）。所以默认用全分辨率。合并模式数据量只有 1/4、噪声更低，但整页实拍字号小的乐谱时会全部失败（第 2.1 节），因此只能用于预览，不能送识别。
- **清晰度门槛：** 全分辨率边缘宽度约 5 px 以内，准确率基本不受影响；到 7 px 就降到约 74%。现在的近拍样片大部分区域是 7–9.5 px。如果整页距离下镜头和对焦仍是这个水平，就不够用，需要对准焦、收光圈到 F4–F5.6，必要时换镜头。
