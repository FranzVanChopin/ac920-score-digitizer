# 采集与识别的融合（2026-10-29）

对象：Codex 的采集固件 `release/AC920_IMX477_A4_album1_20261029`（下称 a4_album1），以及识别软件（v16 开发包 + 常驻流水线）。

## 1. 结论

| 阶段 | 做法 | 状态 |
|---|---|---|
| **现在就能用** | 先在采集固件下拍完一组（一首或多首），再启动 Ubuntu，用 `run_album.sh` 一次识别整张卡，每首输出一个 MusicXML | 识别端已完成，桌面和开发板都已验证（第 4 节）；双方固件和程序都不用改 |
| 可选改进 | 采集固件和 Ubuntu 放在同一张卡上，用多重启动寄存器切换，不用换卡 | 需要 Codex 小改，并解决分区空间问题（第 3.2 节） |
| 最终形态 | 采集程序移到 Ubuntu 下运行，拍一页识别一页，边拍边出谱 | 需要 Codex 移植采集程序（第 3.3 节）；识别端已备好 `--watch` 模式，不用再改 |

两边现在不能同时运行：采集固件是 A53 裸机程序，Ubuntu 也要独占 A53，两者都从 SD 卡启动，同一时刻板上只有一个系统。所以融合的关键是照片怎样从采集系统交到 Ubuntu。

## 2. 接口核对：a4_album1 的输出与识别端的要求

| 项目 | 识别端要求（`camera_focus/CAPTURE_INTERFACE.md`） | a4_album1 | 结论 |
|---|---|---|---|
| 分辨率 | 全分辨率，不合并像素 | 4056×2868，`binning: false` | ✓ |
| 格式 | 8 位灰度，无损 | `Grey/SS-PP.bmp`，BMP_GRAY8，由保存的彩照按 BT.601 转换 | ✓ 与识别端自己的转换最多差 1 级灰度，识别结果一致 |
| 预处理 | 不做 CLAHE、二值化和缩放 | `clahe/binarize/resize: false` | ✓ |
| 方向 | 乐谱正立 | `orientation: sensor_native`，A4 纸横躺在画面里 | 由识别端旋转（`--rotate ccw`，见下） |
| 写文件顺序 | 写完再给识别端 | Meta 最后写，`complete: true` 作为完成标记 | ✓ 识别端只处理 `complete: true` 的页 |
| 编号 | — | `SS-PP`：曲目 00–99，页 00–99，长按 S1 换下一首 | 识别端按曲目把各页合成一个乐谱 |

**方向：** 4056×2868 的固定裁切是横向的 A4 比例，只有纸张横躺（长边沿传感器长边）时才能整页入画并保持最高分辨率。10-29 对比样片就是这样拍的，逆时针转 90° 后正立，即原始图像的右边是页面顶端。

Codex 文档里写的"拍摄时须保证整页正立"，如果理解为在横向画面里竖放 A4 纸，页面只能用到 2868 像素的高度，这份乐谱的谱线间距会降到约 13 像素。因此建议：
- **纸张保持横躺，由识别端转正；**
- **相机安装固定，页面顶端始终朝同一侧。** 如果改了安装方向，改 `--rotate` 即可（`cw`、`180`、`none`）；
- 识别端会检查转正后的谱线是否为水平方向，方向错 90° 时在日志里提示。上下颠倒（180°）检查不出来。

## 3. 三种融合方式

开发板现状（10-29 只读查看）：
- SD 卡（mmcblk1，14.6 GB）：p1 是 FAT32 启动分区（300 MB），p2 是 Ubuntu 根分区（ext4，4.7 GB，剩余 734 MB），其余约 9.6 GB 未分区；
- 板载 eMMC 上另有一套厂商 Linux，与本项目无关，不要动；
- Ubuntu 已加载一个摄像头设计：MIPI CSI-2 RX → VPSS → 帧缓存，对应 `/dev/video0`。它驱动的是 i2c-0 上的 **OV5647**，不是 IMX477。设备树里为 PL 预留了内存（`buffer@40000000`、`reserved_pl_*`），FPGA manager 可以在运行时加载比特流。

### 3.1 两次启动，SD 卡交接（现在就能用）

1. 用采集卡（FAT32，装 a4_album1 的 BOOT.BIN）启动，拍完一组；短按拍一页，长按换下一首。
2. 断电，换回 Ubuntu 卡（或换回 Ubuntu 的 BOOT.BIN），启动 Ubuntu。
3. 让 Ubuntu 能读到采集卡，任选一种：
   - USB 读卡器插在开发板 USB-A 口：桌面环境下会自动挂载到 `/media/fpga/<卷标>`；只有命令行时，由用户输入 `sudo mount -o ro /dev/sdX1 /mnt/capture`；
   - 在电脑上把采集卡的 `Grey/` 和 `Meta/` 两个文件夹拷到 U 盘，再插到开发板。只需要这两个文件夹，`Image/` 彩照用不到。
4. 识别整张卡：
   ```
   sh /home/fpga/<包>/album/run_album.sh /media/fpga/<卷标> /home/fpga/<输出目录>
   ```
   每首得到 `<输出目录>/SS.musicxml`。已识别过的页会跳过，拍了新页后再运行一次即可。

注意：每页彩照加灰度图约 46.5 MB。Ubuntu 卡的启动分区只有 300 MB，所以采集卡最好是单独一张卡。

### 3.2 同一张卡，多重启动切换（可选，需要 Codex 改动）

ZynqMP 在 SD 启动时，按 CSU 多重启动寄存器（`CSU_MULTI_BOOT`，0xFFCA0010）的值选择启动文件：值为 0 时启动 BOOT.BIN，值为 n 时启动 BOOT000n.BIN。软复位后这个值保留。具体行为要在这块板上实测确认。

做法：
- Linux 的 BOOT.BIN 不动，a4_album1 改名为 `BOOT0001.BIN` 放进同一个启动分区；
- Ubuntu 切换到采集：写入 1，然后 reboot（需要用户输入 sudo）；
- 采集切回 Ubuntu：Codex 让空闲的 S3 键写入 0，然后系统复位。

难点：
- 照片要有地方存。启动分区只有 300 MB，只够约 6 页（含彩照）。需要在未分区的 9.6 GB 里新建一个 FAT32 数据分区，这要改分区表，由用户决定；采集固件的 FatFs 也要改为写入这个分区。只存灰度图也能省下 3/4 的空间。
- Linux 下能否直接写这个寄存器（固件隔离设置），要上板确认。

### 3.3 采集程序移到 Ubuntu 下（最终形态，边拍边识别）

把 a4_album1 的采集逻辑改为 Ubuntu 下的用户态程序：
1. 通过 FPGA manager 和设备树覆盖加载 Codex 的比特流（替换现在的 OV5647 设计），用 UIO 暴露各个 IP 的寄存器；
2. 帧缓存放在设备树预留的内存里；
3. IMX477 的 I2C 寄存器通过 `/dev/i2c-*` 写入，S1 按键通过 GPIO 读取，HDMI 预览仍由 PL 输出；
4. 照片照原样写到 ext4 上的 `Grey/` 和 `Meta/`。

识别端运行：

```
run_album.sh <采集目录> <输出目录> --watch 1
```

识别端常驻：每拍完一页（Meta 写好），约 1 秒内开始识别；普通页约 23 秒出结果，《月光》这样的密集页约 35 秒；连拍时，下一页的网络推理与上一页的后续计算重叠。识别端为此已经完成，不用再改。

代价：Codex 要移植裸机代码（中断改为轮询或 UIO，FatFs 改为普通文件，Xil 驱动改为 mmap 寄存器），估计需要数天。拍照时的 CCM 在 PS 上计算，会和识别抢 CPU，单张照片影响约 1–2 秒。

不推荐的做法：沿用厂商的 V4L2 管线、给内核加 IMX477 驱动。这需要为这个内核编译模块，板上没有内核头文件，风险最大。

## 4. 识别端：album 模式（本目录）

| 文件 | 作用 |
|---|---|
| `omr_album.py` | 扫描 `Meta/SS-PP.json`（只处理 `complete: true` 的页）→ 把 `Grey/SS-PP.bmp` 转正后写入工作目录 → 交给常驻识别进程（`run_page.py --serve --pipeline`，最多同时 2 页）→ 每页结果放在 `pages/SS-PP_<sha8>/`，然后把这首曲子已完成的各页重新合成为 `SS.musicxml`；状态写入 `album.json` |
| `merge_pages.py` | 多页合成：小节号连续重编；属性只保留有变化的（拍号、调号、谱号等）；第 2 页起加 `<print new-page="yes"/>`。默认先对每页做 engrave，`--plain` 时不做 |
| `engrave.py`（10-30） | 给合成的乐谱加上显示用的信息：谱号和调号（取该页各行谱的多数，来自 page.musicxml 旁边的 headers.json）、临时记号（按小节、按谱表、按调号判断）、音符类型、附点、三连音、按拍分组的符杠（含十六分音符的第二道符杠）、整小节休止符、声部名 Piano。发声的音高、时值、声部、谱表都不改；`page.musicxml` 本身也不改 |
| `check_engrave.py` | 验证：把同一组页分别做普通合成和 engrave 合成，逐小节比较发声的音符，并检查符杠是否成组开合 |
| `run_album.sh` | 开发板入口，参数与 v16 相同，工作目录默认放在 `/dev/shm`（内存） |

行为：
- **断点续接：** 按 Grey 文件的 sha256 判断，已识别过的页跳过；中断的页下次重做。失败的页在同一次运行里不重试，下次运行时再试一次。
- **方向（10-30）：**
  - **问题：** 单卡支架的测试照片放反了，原来的 `ccw` 把它们转成了上下颠倒，识别结果只有 0.6%；改成 `cw` 后是 66.5%（见 `../studio_review/README.md`）。
  - **用户决定固定为 `ccw`（默认），由拍摄界面标出乐谱上方：** 原方向图像和预览里，乐谱顶端都朝右（见 `../studio_review/ORIENTATION_REQUEST.md`）。
  - **放反时的提示：** 一页的大多数行谱都没找到谱号时，`album.json` 记 `orientation_suspect: true`，日志里也提示可能放反了。
  - **记录：** 每页记录所用方向和谱号找到的比例（`rotate_used`、`clef_ratio`、`attempts`）。改了 `--rotate` 后，旧方向的结果会重做。
  - **备用模式 `--rotate auto`：** 把这样的页转 180° 重新识别，保留谱号找到得多的那次，之后的页沿用这个方向。
- **超时保护：** 一页超过 `--page-timeout`（默认 600 s，开发板正常约 25 s）还没有结果时，结束识别进程（连同它派生的解码进程），把这页记为失败，重启识别进程继续处理后面的页。
- **拍号延续：** 同一首的后一页使用前一页的拍号作为默认值（`run_page.py` 新增的 `METER=@prev`，只在常驻模式下生效）；页面上有拍号或能从内容推断时，以页面为准。
- **只读采集卡：** 输出目录不能放在采集目录里面。

`run_page.py` 的两处改动（单页运行的路径不变，grey_1 的输出与改动前逐字节相同，sha256 `621db90a`）：
1. 常驻模式的第三列可以填 `@prev`。
2. **修复流水线模式的死锁。** 流水线模式下有一个读取线程，会阻塞在标准输入（管道）的读操作上，并持有 `sys.stdin` 的缓冲锁。解码阶段 fork 出的 4 个进程（multiprocessing），第一件事就是关闭 `sys.stdin`；子进程继承了这把已被占用的锁，于是永远等下去。
   - 10-27 的开发板测试是从文件读标准输入，读取线程很快就读到文件末尾、释放了锁，所以当时没有出现。
   - 这次 album 模式让管道一直开着，开发板上第一页就卡住了：4 个子进程停在 futex 上，fd 0 还是管道。
   - 修复：读取线程改为持有原来的标准输入对象，`sys.stdin` 换成 `/dev/null`。

- 曲目 02：`complete: false`。

**桌面（10 页）：**
- 曲目 02 被跳过；
- 00-00 的输出与单独运行 grey_1 逐字节相同；
- 合成：00 共 6 页 123 小节，01 共 3 页 63 小节。各小节内容与原页完全相同，编号 1..n 连续；中间一页识别出的 5/4 拍号被保留，下一页又恢复为 4/4；

  - 有了调号、符杠和临时记号，第 1 页从 4 个小节变成 5 个小节；

**开发板（10-29，`board_trial/board_album/`）：**

测试卡取了 7 页：00-00、00-01、00-04、01-00…01-02，以及未完成的 02-00。包放在 `/home/fpga/claude-album-20261029b`，命令是 `sh album/run_album.sh <卡> <输出>`。

  - 6 页全部完成，02-00 被跳过；

结论：桌面评估可以代表开发板上的准确率，但相机照片的输出不再与开发板逐字节相同。
